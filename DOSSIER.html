1. Mapa SSDLC — Secure Software Development Life Cycle

Diagrama de las seis etapas aplicadas al sistema Gestión de Tareas API, con las amenazas identificadas (STRIDE) y los controles de seguridad implementados en cada fase.

📋 E1

Requisitos de Seguridad

Fase 1

⚠ Amenazas

  • • Requisitos incompletos → funciones inseguras
  • • Ausencia de RBAC desde el diseño
  • • Validación de datos no definida

✅ Controles

  • • DTOs Pydantic con extra="forbid"
  • • 5 requisitos formales (RS-01 a RS-05)
  • • RBAC: roles admin / docente / estudiante
↓
🏗️ E2

Diseño Seguro

Fase 2

⚠ Amenazas

  • • Spoofing de identidad (JWT sin revocación)
  • • Elevation of Privilege (sin IDOR check)
  • • Tampering de datos sin autorización

✅ Controles

  • • JWT con jti UUID único por sesión
  • • STRIDE aplicado en modelado de amenazas
  • • Arquitectura 3 capas: API / Lógica / DB
↓
💻 E3

Codificación Segura

Fase 3

⚠ Amenazas

  • • Inyección SQL (CWE-89)
  • • IDOR – Acceso a recursos ajenos (CWE-284)
  • • XSS por renderizado sin escape (CWE-79)
  • • Fuerza bruta sin limitación

✅ Controles

  • • Prepared Statements (? params)
  • • Anti-IDOR: HTTP 403 si owner_id ≠ user_id
  • • bcrypt con factor 12 de costo
  • • Rate Limiter progresivo (30s / 180s)
↓
🧪 E4

Pruebas de Seguridad

Fase 4

⚠ Amenazas

  • • Código con vulnerabilidades no detectadas
  • • SAST sin analizar patrones peligrosos
  • • Pruebas negativas no ejecutadas

✅ Controles

  • • 19 pruebas pytest (100% passing)
  • • Bandit SAST: B608 CWE-89 en app_vulnerable
  • • Pylint: W0612 — variable IDOR sin uso detectada
  • • app_segura.py → 0 issues en Bandit
↓
🚀 E5

Despliegue Seguro

Fase 5

⚠ Amenazas

  • • Comunicación sin cifrado (HTTP)
  • • CORS permisivo (acceso desde cualquier origen)
  • • Headers de seguridad ausentes

✅ Controles

  • • HTTPS forzado en Render.com
  • • CORS regex: sólo orígenes autorizados
  • • Security Headers middleware (X-Frame, CSP, HSTS)
↓
🔍 E6

Operación y Monitoreo

Fase 6

⚠ Amenazas

  • • Ataques sin registro ni trazabilidad
  • • Tokens comprometidos sin revocación
  • • Fuerza bruta sin alertas

✅ Controles

  • • audit.log sin payload malicioso
  • • token_version: revocación de sesión al cambiar contraseña
  • • Rate limiter bloquea y registra IPs sospechosas
2. Requisitos de Seguridad

Cinco requisitos verificables definidos a partir del análisis de amenazas STRIDE. Cada requisito es trazable a un caso de prueba automatizado en test_security.py.

ID Requisito de Seguridad Amenaza STRIDE CWE Prioridad Prueba de Aceptación
RS-01

Control Anti-IDOR

El sistema debe verificar que el usuario autenticado sea propietario del recurso antes de permitir modificación o eliminación.

 Elevation of Privilege CWE-284 CRÍTICA Solicitar DELETE /tasks/{id_ajeno} retorna HTTP 403. Verificado en test_03_idor.
RS-02

Prevención de Inyección SQL

Todas las consultas a la base de datos deben usar Prepared Statements con parámetros parametrizados.

 Tampering de datos CWE-89 CRÍTICA Búsqueda con ' OR 1=1 -- retorna lista vacía []. Verificado en test_17_sqli.
RS-03

Almacenamiento Seguro de Contraseñas

Las contraseñas deben almacenarse con hash bcrypt de factor de costo 12. Nunca en texto plano.

 Information Disclosure CWE-256 CRÍTICA El campo password en DB inicia con $2b$12$. Verificado en test_01_register.
RS-04

Rate Limiting Progresivo

Tras 3 intentos fallidos de login, el sistema debe bloquear el acceso progresivamente (30s / 180s).

 Denial of Service / Spoofing CWE-307 ALTA 4.º intento fallido retorna HTTP 429 con retry_after. Verificado en test_06_brute.
RS-05

Revocación de Sesión por token_version

Al cambiar la contraseña, el sistema debe invalidar todos los tokens JWT emitidos anteriormente.

 Repudiation / Spoofing CWE-613 ALTA Token viejo tras cambio de contraseña retorna HTTP 401. Verificado en test_09_revoke.
CRÍTICA Riesgo inaceptable, debe corregirse antes del despliegue
ALTA Riesgo significativo, debe mitigarse en esta iteración
MEDIA Riesgo aceptable a corto plazo con monitoreo

Comparativa de código vulnerable vs. código seguro. Los archivos app_vulnerable.py y app_segura.py están en el repositorio para verificación.

Vulnerabilidad 1 — Inyección SQL (CWE-89)

Bandit reporta B608 en app_vulnerable.py línea 49

✗ ANTES — Código Vulnerable
# app_vulnerable.py — línea 49 # ⚠ Bandit: B608 CWE-89 Medium @app.route("/tareas") def listar_tareas(): user_id = request.args.get("user_id") # ⛔ Interpolación directa → SQLi query = f"SELECT * FROM tareas WHERE user_id = {user_id}" cur.execute(query) return jsonify(cur.fetchall())
✓ DESPUÉS — Código Seguro
# app_segura.py — Prepared Statement # ✅ Bandit: 0 issues @app.route("/tareas") def listar_tareas(): user_id = request.args.get("user_id") # ✅ Parámetro separado → imposible SQLi cur.execute( "SELECT * FROM tareas WHERE user_id = ?", (user_id,) ) return jsonify(cur.fetchall())
🟠

Vulnerabilidad 2 — IDOR / Broken Access Control (CWE-284)

Pylint reporta W0612 — variable user_id_session definida pero nunca usada

✗ ANTES — Código Vulnerable
# app_vulnerable.py # ⚠ Pylint W0612: unused variable @app.route("/tareas/<id>", methods=["DELETE"]) def eliminar_tarea(id): # ⛔ Se obtiene pero NUNCA se verifica user_id_session = session.get("user_id") cur.execute( f"DELETE FROM tareas WHERE id={id}") return "Eliminado"
✓ DESPUÉS — Código Seguro
# app_segura.py + main.py # ✅ Verifica propietario antes de eliminar @app.route("/tareas/<id>", methods=["DELETE"]) def eliminar_tarea(id): user_id = session.get("user_id") cur.execute( "SELECT owner_id FROM tareas WHERE id=?", (id,)) tarea = cur.fetchone() if tarea["owner_id"] != user_id: abort(403) # HTTP 403 Forbidden cur.execute("DELETE FROM tareas WHERE id=?", (id,))

5. Conclusiones y Evidencias

💡 Reflexión del Equipo

🔒 Seguridad desde el diseño (Shift-Left)

Implementar STRIDE y los requisitos de seguridad (RS-01 a RS-05) desde la fase de requisitos nos permitió anticipar vulnerabilidades críticas como SQLi e IDOR antes de escribir la primera línea de código, reduciendo el costo de corrección hasta 10× frente a detectarlas en producción.

🤖 Valor del análisis estático (SAST)

Bandit detectó automáticamente CWE-89 (B608) en app_vulnerable.py y CWE-94 (B201), dos vulnerabilidades que un revisor humano podría omitir. La comparación entre la app vulnerable y la segura demostró que 0 issues en Bandit es un indicador tangible de mejora en calidad de código.

🧪 Pruebas negativas como red de seguridad

Las 19 pruebas automatizadas —incluyendo pruebas negativas que inyectan payloads maliciosos reales— garantizan que cada refactorización del código no rompa los controles de seguridad. Este enfoque permite evolucionar el software con confianza.

🚀 Despliegue seguro y observable

La combinación de HTTPS en Render, Security Headers middleware, CORS regex restrictivo y audit.log estructurado transforma el sistema de una API básica en un servicio observable y defendible en producción, cumpliendo con los requisitos OWASP Top 10.
